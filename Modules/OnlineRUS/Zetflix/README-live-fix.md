# Zetflix: самообновляемые ссылки на поток (правка 16.10.2026)

## Симптом
Во время просмотра через источник **Zetflix** плеер через несколько минут падал с
`details [fragLoadError] fatal [true]`; картинка/звук какое-то время ещё шли из буфера
(«как с Фантомом» — у него та же схема выдачи ссылок).

## Что показали логи и замеры
1. **403 отдаёт CDN площадки**, а не наш сервер: тело ответа — стандартная страница
   `403 Forbidden … <center>nginx</center>` (192/548 байт), заголовок `PX-Cache: BYPASS`.
   lampac просто пробрасывал ответ.
2. **Ссылки площадки живут 5–7 минут.** Замер: свежая ссылка, которую я дёргал раз в
   45 секунд (1 КБ Range + плейлист), умерла через **5 мин 35 с** (23:09:39 → 23:15:14).
   Сессии плеера: 22:55:09 → 23:02:20 (7:11), 23:05:08 → 23:08:27 (3:19),
   15.10: 07:58:30 → 08:03:28 (4:58), 15:55:57 → 16:01:11 (5:14).
   После истечения 403 отдают **и сегменты, и сам плейлист**.
3. **CDN принимает только «свой» выходной IP.** Прямой запрос с сервера — 403,
   тот же URL через прокси модуля `127.0.0.1:40000` (Cloudflare WARP, `warp-svc`) —
   200. Матрица на одной сегментной ссылке:
   `direct=403/548; warp=200/3976780; sameSession(без прокси)=403`.
4. **Сегменты привязаны к тому же выходу, что и манифест.** Плейлист, полученный через
   WARP, можно тянуть только через WARP; попытка отдать сегмент через общий `/proxy`
   лампы (другой выход) давала 403.
5. Наш модуль раньше один раз «запекал» ссылку площадки и заголовки
   (`Origin`/`Referer`/`User-Agent`/`Accepts-Controls`) в прокси-линк
   (`HostStreamProxy(...)`) — поэтому через несколько минут всё начинало сыпаться 403.

## Что сделано (файл `Controller.cs` модуля Zetflix)
Плееру больше не отдаётся застывшая ссылка — он ходит в наш маршрут
`GET /lite/zetflix/stream`:

* `Video()` формирует для каждого качества ссылку `…/lite/zetflix/stream?k=p&q=<key>&lvl=-1&u=<b64>&ctx`
  (через `accsArgs`, как и остальные ссылки модуля);
* маршрут на каждый запрос заново получает данные у площадки (кэш 50–60 с),
  заново берёт краевой токен (`ZetflixGuard.GetTokenAsync()`), подтягивает свежий
  мастер-плейлист и переписывает **все** URI (варианты, сегменты, `EXT-X-MAP`,
  ключи/`EXT-X-MEDIA`) на наш маршрут. Учитываются относительные пути
  (`index-f1-v1-a1.m3u8`) и резервные зеркала через `" or "`;
* сегменты и init-карту модуль **отдаёт сам** (`LiveStreamBytes`) через тот же
  WARP-прокси, что и манифесты, с поддержкой `Range` (206 + `Content-Range`);
* добавлены повторы (2–3 попытки) — WARP сегодня дважды «икал» (502 на CONNECT и
  `connection refused`);
* диагностические маршруты `dbg`/`dbg2` и запись в `/tmp/zetflix-live.log` из финальной
  сборки удалены.

## Финальные штрихи
* мастер-плейлист кэшируется 45 с (`LiveFetchPlaylist(..., cacheKey)`) — раньше он тянулся
  у площадки на **каждый** запрос плеера, что давало лишние обращения и, судя по картине
  отказов, часть 403 от CDN;
* при сбое любого звена — повторный резолв «с нуля» (сегмент/вариант), сетевые сбои
  прокси повторяются 2–3 раза.

## Проверка
* Полный цикл: мастер 200 → вариант 200 (241 сегмент) → сегмент **200 / 3 976 780 байт
  `video/mp4`** → init-карта 200 / 1 140 байт.
* Прогон 9 минут (та же ссылка на плейлист и тот же сегмент каждые ~6,5 с):
  **67 из 67 запросов — 200** (старая схема умирала на 5–7 минуте).
* Реальный клиент (тест владельца 23:42–23:44): 12 запросов к новому маршруту, все
  **206** (включая перемотку: `i=-1` init + `i=18..20`).
* CORS отдаётся (ламповый middleware), `Cache-Control: no-store`, `Accept-Ranges: bytes`.
* Финальный реалистичный прогон (плейлист взят **один раз**, дальше только сегменты по
  порядку, как у плеера): **91 сегмент из 91 — 206** за 476 секунд (≈8 минут), то есть
  плейлист, снятый один раз, продолжал давать рабочие сегменты далеко за прежним
  рубежом 5–7 минут. Ошибок 403 в логах nginx за это время нет.

* Правки модуля подхватываются **только при рестарте lampac** (`WatchersDynamicModule`
  вложенные модули `OnlineRUS/Zetflix` не отслеживает — проверено записью файла,
  `touch` манифеста и атомарным `mv`). lampac перезапускался 5 раз в ходе работы.
* Бэкап исходной версии модуля: `/home/lampac_backups/module/Zetflix-20261016-231659-prelive`.
  Откат: вернуть `Controller.cs` из бэкапа и перезапустить lampac.
* Проверка компиляции до деплоя (Roslyn с сервера):
  `dotnet /usr/share/dotnet/sdk/*/Roslyn/bincore/csc.dll -target:library -r:/home/lampac/Shared.dll -r:/home/lampac/Core.dll …`
* **Зависимость:** источник ходит к площадке только через `127.0.0.1:40000`
  (`warp-svc`). Если WARP недоступен — Zetflix будет отдавать 503 (модуль повторяет
  запросы). Прямой IP сервера площадка режет 403.
